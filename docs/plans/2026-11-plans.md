## 2. Metal: what remains

By priority:

1. **Missing present paths in the Metal hook.** MoltenVK needs no support of its own: it is Metal, and detection sees it as Metal. But the hook only draws in `-[MTLCommandBuffer presentDrawable:]`, while MoltenVK (`MVKImage.mm`, `presentCAMetalDrawable`) calls `-[CAMetalDrawable present]`/`presentAtTime:` from a scheduled handler, as Apple recommends. A native Metal app may do the same, or use `presentDrawable:atTime:`/`afterMinimumDuration:`. In all these cases the hook never gets `Ready`.
   - Step 1: hook the two command buffer variants (same handling, same class as `presentDrawable:`).
   - Step 2: hook `-[CAMetalDrawable present]`, `presentAtTime:` and `presentAfterMinimumDuration:` (stable public QuartzCore class). The application's command buffer is already committed then: encode the overlay in our own command buffer, on the same queue so that it runs after the application's rendering. Find the queue by wrapping the blocks given to `addScheduledHandler:` (we then know which command buffer we are in), or else from the last `commit` seen. Then present with `presentDrawable:` (or `presentDrawable:atTime:`) instead of the original `present`, with a recursion guard.
2. **`Removing` never fired.** `MetalHook_t::_ResetRenderState` is never called: a recreated window or device is never detected and `OverlayHookReady(Removing)` only comes with the destruction. Compare `commandBuffer.device` and `drawable.layer` with the first frame's, and go through `Reset`/`Removing` when the layer goes away.
3. **AppKit thread and inputs** (M4, shared with macOS OpenGL). The event monitor runs on the main thread and feeds ImGui's input queue while the game's render thread runs `ImGui::NewFrame`: a data race, crashing games that render off the main thread (Unity, Unreal, most engines).
   - Proposed fix: a mutex in `NSViewHook_t`, held around `ImGui_ImplOSX_HandleEvent` (main thread) and around `ImGui::NewFrame` only (render thread). No AppKit call is made under the lock on the render side, so no deadlock with the main thread.
   - The OSX backend's activation notifications (`io.AddFocusEvent`) stay outside the lock: a change for the fork.
   - Reproduced by the `render_thread_events` scenario (rendering on a secondary thread, mouse events posted to the application): `abort` within seconds.
4. **Target window** (M4). `[NSApp _mainWindow]` is a private selector, and a `nil` window on the first frame (application inactive at launch, for example) is never retried. Start from the presented drawable instead (`layer.delegate` is the `NSView` of a layer-backed view) and retry while the window is `nil`.
5. **Incomplete input hiding** (M5). Wheel, other buttons and `NSEventTypeFlagsChanged` are not blocked. The key combination is only checked on `KeyDown`: Shift pressed after F2 does nothing.
6. **Detection on dual GPU Macs.** `fix/metal-detection-any-gpu` creates a queue on every GPU, which may power up the discrete GPU of an Intel MacBook Pro. If that matters, start with the low power GPU and only instantiate the discrete one when needed, or derive the class name from the device's.
7. **macOS OpenGL delay** (about 11 s before `Ready`, immediate with Metal): to investigate, it happens during detection.

## 3. Remaining prioritised bugs (three platforms)

From a full review of the Windows and Linux hooks, ranked by impact. Ids come from the earlier report when they exist.

### All platforms: keys and buttons stuck in the game

On the three platforms, releases (`WM_*UP`, `KeyRelease`/`ButtonRelease`, `NSEventTypeKeyUp`/`*MouseUp`, Windows raw input) are swallowed while the overlay is open. A player holding W while opening the overlay keeps walking after closing it.

Passing every release would click through the overlay: some game UIs act on a release alone. So track what the application saw:
- while the application's inputs are visible, record the keys and buttons pressed that it received;
- once hidden, only pass the release of a key or button the application believes pressed.

For Windows raw input, the same in `GetRawInputData`/`GetRawInputBuffer`:
- keyboard: pass the `RI_KEY_BREAK` blocks of pressed keys;
- mouse: keep only the `*_UP` flags and zero the motion;
- `GetRawInputBuffer`: compact the buffer, like `fix/toggle-keys-reach-app` does.

On the ImGui side, call `io.ClearInputKeys()` when the overlay's inputs get hidden (Linux NEW-5, Windows NEW-4).

## 4. Wayland (#60)

### Situation

- A game running under XWayland already works through the X11 hook: SDL2 by default, GLFW when X11 is forced.
- SDL3 and GLFW 3.4 pick native Wayland when the session offers it:
  - with OpenGL the game goes through EGL, which isn't detected at all;
  - with Vulkan detection succeeds but no X window is found. Since `fix/vulkan-window-search-throttle` that is one search per second.
- Immediate workaround to document: `SDL_VIDEODRIVER=x11`, or the `GLFW_PLATFORM_X11` hint.

### Why not `recvmsg`

The issue proposes to hook `recvmsg` and decode the protocol stream:
- Hiding an input from the game means removing messages from the stream while keeping the file descriptors (`SCM_RIGHTS`) and libwayland's object map consistent.
- Object creation and destruction must be followed to know which id is a `wl_pointer` (`wl_registry.bind`, `wl_seat.get_pointer`...). Those requests go through `sendmsg`, not `recvmsg`.
- A message may be split across two reads.

Keep it as a last resort for a statically linked libwayland, which is rare: libwayland-client is shared with Mesa's EGL and Vulkan drivers.

### Proposed approach: wrap the listeners

libwayland-client is a stable shared library that every toolkit calls.

1. **Phase 0 (done):** a Wayland game must not lose frames or crash. The X walk is throttled; `X11Hook_t::StartHook` should also stop requiring libX11 for a Wayland game.
2. **Phase 1, rendering:**
   - EGL detection: hook `eglSwapBuffers` and `eglSwapBuffersWithDamageKHR`/`EXT` in `libEGL.so.1`, with an `EGLHook_t` sharing `OpenGLHookCommon_t`.
   - The EGL surface gives the framebuffer size (`eglQuerySurface` `EGL_WIDTH`/`EGL_HEIGHT`).
   - For the window: hook `wl_egl_window_create` (`libwayland-egl.so.1`), which ties the `wl_surface` to the `wl_egl_window` then given to `eglCreateWindowSurface`.
   - Vulkan: hook `vkCreateWaylandSurfaceKHR` (and `vkCreateXlibSurfaceKHR`/`vkCreateXcbSurfaceKHR` while at it, which removes the `_NET_WM_PID` search). That gives the `wl_display` and `wl_surface`.
3. **Phase 2, inputs:**
   - Hook `wl_proxy_add_listener` and `wl_proxy_add_dispatcher`, and identify the `wl_pointer`, `wl_keyboard` and `wl_touch` proxies with `wl_proxy_get_class`.
   - Replace their listener table with ours, which feeds ImGui then calls the application's unless its inputs are hidden.
   - Hiding the game's inputs: send it `wl_pointer.leave` and `wl_keyboard.leave` when hiding, then `enter` (with the pressed keys) when showing. The game releases its keys cleanly, which solves stuck keys without tracking state.
   - Keyboard: the keymap comes as a file descriptor (`wl_keyboard.keymap`); compile it with libxkbcommon (dlopen) for characters. Key repeat is client side (`repeat_info`).
   - Pointer: Wayland has no position query. The position comes from `motion` in surface coordinates (`wl_fixed_t`), and the framebuffer scale from the EGL or swapchain size.
   - The cursor belongs to the game: use `io.MouseDrawCursor = true`.
4. **Phase 3, comfort:** clipboard (`wl_data_device`), IME (`zwp_text_input_v3`), `wp_fractional_scale` for the scale.

### Code and tests

- A `WaylandHook_t` next to `X11Hook_t`, chosen from the surface the renderer hook sees (`NativeWindow_t` becomes an X11/Wayland variant), and a small ImGui platform backend. No Wayland backend exists upstream: write it in our code, or in the fork for the generic parts.
- Tests on the VM (GNOME Wayland session): the GLFW + GL host and a Vulkan variant with `GLFW_PLATFORM_WAYLAND`; SDL3 test apps if added.

## 5. Metal 4 (#73)

Metal 4 needs macOS 26 and Apple Silicon. No test machine is available (the test Mac is an Intel one on macOS 12): **the developer has to test it**.

### Application side API

- `MTL4CommandQueue` (`[device newMTL4CommandQueue]`) and `MTL4CommandBuffer`, with `beginCommandBufferWithAllocator:`/`endCommandBuffer`.
- Submission with `[queue commit:count:]`.
- Drawable synchronisation: `[queue waitForDrawable:]` before writing, `[queue signalDrawable:]` after the commits, then `[drawable present]`.
- Resources made resident by `MTLResidencySet`s, bound through `MTL4ArgumentTable`s, explicit barriers.

### Plan

The Metal 4 API names below must be checked against the macOS 26 SDK when implementing.

1. **Build.**
   - Build `deps/ImGui/backends/imgui_impl_metal4.mm` (already in the fork) with ARC.
   - Guard with `__has_include(<Metal/MTL4CommandQueue.h>)` and `@available(macOS 26.0, *)`. The `macos-latest` CI needs the 26 SDK, otherwise the code is compiled out.
2. **Detection.** A pure Metal 4 application never calls `-[MTLCommandBuffer commit]`.
   - As in `fix/metal-detection-any-gpu`, create an `MTL4CommandQueue` on each GPU (if it `respondsToSelector:@selector(newMTL4CommandQueue)`).
   - Hook its class's `commit:count:` (and `commit:count:options:`), then `signalDrawable:`.
3. **Rendering (`Metal4Hook_t`).** In the `signalDrawable:` hook, the application has committed all its work on the drawable:
   - record our `MTL4CommandBuffer` (one allocator per frame in flight, 3 by default);
   - encode an `MTL4RenderPassDescriptor` pass on `drawable.texture` with `loadAction = Load`;
   - start with a queue barrier (`barrierAfterQueueStages:` fragment → fragment) to wait for the application's writes to the drawable;
   - call `ImGui_ImplMetal4_RenderDrawData`, which manages its own `MTLResidencySet` and adds our textures when used;
   - commit to the same queue, then call the original `signalDrawable:`.
4. **Resources.** Texture ids are `MTLTexture`s like with Metal 3: `MetalHook_t::_LoadResources` can be reused through a common base.
5. **Screenshots.** Copy with an `MTL4ComputeCommandEncoder` (`copyFromTexture:toBuffer:`) in our command buffer, with the same pending logic as `fix/metal-screenshot`.
6. **Risks.**
   - Wrong barrier or residency: artefacts or GPU faults, to validate with the Metal 4 validation layer.
   - An application mixing Metal 3 and Metal 4 queues must keep a single overlay: the first present seen wins.

## 6. #94: `GetPhysicalCursorPos` / `SetPhysicalCursorPos`

- **Finding** (checked on Windows 11 26200): user32's `GetPhysicalCursorPos`/`SetPhysicalCursorPos` exports have the same address as `GetCursorPos`/`SetCursorPos`, in x64 and WOW64. Since Windows 8.1 the existing inline hooks already cover them, and hooking them again would detour the same address twice. They were separate functions (physical coordinates) only on Windows 7 and 8.0.
- **Plan:**
  1. Resolve the "Physical" exports as optional and only hook them when their address differs.
  2. Keep a single saved position and convert with `PhysicalToLogicalPoint`/`LogicalToPhysicalPoint` (Vista+).
  3. Also hook `GetCursorInfo`: its `ptScreenPos` still gives the real position when inputs are hidden.
  4. Prerequisite: `fix/windows-hidden-cursor-position`, which fixes the position returned after a `SetCursorPos`.
- Once that prerequisite is merged, the issue can be closed with this finding, or after `GetCursorInfo` is added.

## 7. #67: Metal memory leak

- **Main cause found and fixed** (`fix/metal-objc-arc`): the ImGui Metal backend built without ARC.
  - Measured on `macos_metal_app`, overlay visible: 37 → 141 MB in 30 s before, 19 → 19 MB after.
  - The cache re-enabled in the fork (`fix/metal-pipeline-cache`) also avoids a pipeline per frame.
- **Second source**, fixed by `fix/metal-drawable-target`: the `_RenderPass` list retained the command buffers of any application that doesn't present with `presentDrawable:`.
- **To do:** check on Apple Silicon, then close the issue after merging.
